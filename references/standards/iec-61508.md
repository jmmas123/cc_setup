# IEC 61508 — Translated (Functional Safety Spirit)

**Source:** IEC 61508:2010, "Functional safety of electrical/electronic/programmable electronic safety-related systems," Parts 1-7. International Electrotechnical Commission. Specifically Part 3 (Software requirements) Annex A/B technique tables and Part 7 informative techniques.

**Citation tag for findings:** `IEC-61508-<principle-key>` where `<principle-key>` is the slug from the table below (e.g., `IEC-61508-fault-detection`).

**Translation philosophy:** IEC 61508 is a process and architecture standard targeting Safety Integrity Levels (SIL 1-4) for safety-critical hardware/software systems. Most of it (process audits, FMEA, PFD/PFH calculations) doesn't apply to typical web/app code. We extract the **7 most code-actionable principles** that map to runtime correctness and review them at the code level. Each principle traces to a specific IEC 61508 Part 3 / Part 7 technique.

## Notes on translation choices

- **Why 7 principles, not 30?** IEC 61508 lists ~80 techniques in Part 7 Annex C. Most are about hardware fault tolerance, formal proof, or process audit (training records, role separation). The 7 above are the *code-actionable* subset visible in a code review; the others are process/architecture concerns that belong in design review, not code review.
- **`bounded-execution`:** Overlaps NASA P10-#2 (loop bounds) intentionally — IEC 61508 frames it as worst-case execution time (WCET); P10 frames it as static loop bound. Both apply; cite the more specific.
- **`tested-under-fault`:** This is the principle behind property-based testing and fuzz testing in modern practice. Hypothesis (Python) and fast-check (JS) are the canonical libraries.
- **`traceability`:** In IEC 61508 this is a documentation/process artifact (a traceability matrix). The code-level approximation is "the function/test cites the requirement it implements."
- **`fail-safe-defaults`:** This principle generalizes Saltzer & Schroeder's 1975 design principle of the same name; IEC 61508 adopts it as Part 7 §C.3.1.

## How the reviewer agent uses this file

For each function/module under review, walk the table and ask "does this code violate this principle?" Tag findings as `IEC-61508-<key>`. Severity guidance:

- **High:** `fault-detection`, `fail-safe-defaults`, `bounded-execution` — runtime safety risks.
- **Medium:** `separation-of-concerns`, `structured-error-handling`, `tested-under-fault` — design/correctness risks.
- **Low:** `traceability` — process gap, not a runtime defect.

## What this file does NOT cover

IEC 61508 process requirements (SIL determination, FMEA, software development lifecycle artifacts, configuration management, third-party SOUP qualification) are out of scope for code review. They belong in architecture review and the project's safety case documentation.
